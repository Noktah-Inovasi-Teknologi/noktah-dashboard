# Quickstart & Validation: Client Knowledge Base

This guide validates the feature end-to-end. It references [data-model.md](./data-model.md) and
[contracts/mcp-tools.md](./contracts/mcp-tools.md) rather than duplicating them. Implementation
details live in `tasks.md` (generated by `/speckit-tasks`).

## Prerequisites

- Docker Desktop running; existing services healthy (`docker-compose ps`).
- `.env` populated with Google OAuth vars (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`,
  `GOOGLE_REFRESH_TOKEN`) and Postgres vars.
- `knowledge-base` service added to `docker-compose.yml` and built.
- `knowledge_records` table + `pg_trgm`/`pgcrypto` extensions created in the app database (via
  `config/postgres/init.sql` on fresh DBs, or the idempotent migration on existing ones).
- The `knowledge-base` MCP server registered in AnythingLLM (remote SSE/HTTP URL on
  `dashboard-networks`) and its tools enabled for the target workspace.

## Setup commands

```bash
# Build and start the new service alongside the stack
docker-compose up -d --build knowledge-base

# Confirm health and MCP endpoint
docker-compose ps knowledge-base
docker-compose logs -f knowledge-base

# Verify the table and extensions exist
docker exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\d knowledge_records"
```

In the AnythingLLM UI, confirm the `knowledge-base` MCP server shows as connected and its tools
(`kb_find_client`, `kb_upsert_record`, `kb_query_current`, `kb_query_history`) are listed.

## Validation scenarios

Each scenario maps to a user story / success criterion. Run them in the AnythingLLM chat with the
KB tools enabled.

### V1 — Ingest plain text (US1, FR-001/003/004, SC-001)

1. In chat: paste "For Acme Corp, billing terms are Net-30, invoiced monthly."
2. **Expected**: chatbot proposes `client_name=Acme Corp`, `subject≈billing terms`, calls
   `kb_upsert_record` → `result: "created"`, and confirms with a summary in < 30 s.
3. Verify: `kb_query_current(client_name="Acme Corp")` returns the record.

### V2 — Ingest Google Doc/Sheet (US1, FR-002, SC-004)

1. In chat: share a Google Docs or Sheets link describing one or more clients.
2. **Expected**: server fetches the source; chatbot extracts records and issues `kb_upsert_record`
   calls with `source_type=google_doc|google_sheet` and `source_reference=<url>`; confirms counts.
3. Verify at least one created record via `kb_query_current`.

### V3 — Retrieve current knowledge (US2, FR-005/006/007, SC-002/003/006)

1. Ask: "What are Acme Corp's billing terms?"
2. **Expected**: answer drawn from the current record in < 15 s; superseded records never surface as
   the primary answer; payload is a few structured rows, not whole documents.

### V4 — Supersession (US4, FR-010)

1. In chat: "Update Acme Corp billing terms: now Net-15, invoiced weekly."
2. **Expected**: `kb_upsert_record` → `result: "superseded"`, `superseded_record_id` set.
3. Verify: `kb_query_current` returns only the Net-15 record; the Net-30 record is absent from
   current results.

### V5 — Historical retrieval (US3, FR-008/009, SC-005)

1. Ask: "What were Acme Corp's billing terms before?"
2. **Expected**: `kb_query_history` returns the Net-30 record labelled `status: superseded` with a
   pointer to the Net-15 record and both timestamps visible.

### V6 — Empty / unknown client (FR-011, SC-003)

1. Ask about a client with no records: "What do we know about Nonexistent Ltd?"
2. **Expected**: chatbot states no information is available (from `found: false`) — no hallucinated
   answer.

### V7 — Client identity reconciliation (FR-003b)

1. In chat: add info for "acme" (lowercase, no suffix).
2. **Expected**: `kb_find_client` returns "Acme Corp" as a close suggestion; chatbot asks the user
   to confirm whether this is the same client before saving.

### V8 — Duplicate dedupe (R6)

1. Re-submit the exact current "Net-15, invoiced weekly" info for Acme Corp billing terms.
2. **Expected**: `kb_upsert_record` → `result: "unchanged"`; no new supersession row created.

## Automated checks (developer)

```bash
# Run the service test suite (supersession, normalization, history, tool contracts)
docker exec knowledge-base uv run pytest -q
```

- `test_repository.py`: supersession atomicity, single-current-per-(client,subject) invariant,
  normalized client matching, history retrieval with status labels.
- `test_tools.py`: each MCP tool's argument validation and return shape against
  [contracts/mcp-tools.md](./contracts/mcp-tools.md).
- `test_ingestion.py`: Google source fetch/normalization helpers (mocked Google API).
