# Post-Deployment Baseline — 2026-08-03

Recorded immediately after migration 008 and the legacy seeding were applied to
`noktah_dashboard`. **This is the "before" for next month's comparison** (SC-005),
which is the first point at which this feature can actually be validated.

## Store state at deployment

| Measure | Value |
|---|---|
| `harvested_signals` rows | 819 |

| Observation timestamp range | 2026-07-15 → 2026-08-01 |

The observation timestamps are the rows' real `harvested_at` values, **not** the

## `velocity_status` distribution

At migration time, before any refresh had run:

| Reason | Count |
|---|---|
| `legacy_only` | 817 |
| `never_observed` | 2 |
| **`UNRESOLVED`** | **0** |

After the live `lasikasyik` validation run later the same day:

| Reason | Count |
|---|---|
| `legacy_only` | 775 |
| `observed_once` | 140 (newly discovered, never harvested) |
| `has_velocity` | 42 |
| `never_observed` | 2 |
| **`UNRESOLVED`** | **0** |

All 819 signal rows are classified — none falls outside the view. Zero
`UNRESOLVED` is the FR-024 guarantee holding in production.

**A store that is entirely `legacy_only` is the CORRECT day-one state.** Velocity
needs two observations of the same item and the second arrives with the next
monthly harvest. `velocity-derive` reports this explicitly rather than as a
silent zero:

```
velocity-derive: items=817 derived=0 ... insufficient_observations=817
WARNING: No intervals derived: all 817 item(s) still have a single observation.
```

## The reach ceiling — corrected after the live run

Phase 0 estimated this from `list_depth = 30` and reported 252 rows permanently
frozen. **That was wrong.** The monthly deployments run
`social_harvest_window.py`, whose `DEFAULT_LIST_DEPTH = 150`, and none overrides
it. No account holds more than 69 harvested items.

| | Rows |
|---|---|
| Reachable at the actual depth (150) | **819 (100%)** |
| Permanently frozen | **0** |

Confirmed live: one `lasikasyik` listing returned **182** items — Instagram merges
the posts and reels tabs, so the count can exceed the requested depth.

The ceiling is still real; it is simply far higher than first stated. An item that
does fall out of reach is recorded as `aged_out_of_listing`.

## Live validation (T022) — 2026-08-03

One real listing against `https://www.instagram.com/lasikasyik/` with `--days 1`,
chosen so the depth filter selects nothing to download:

```
lasikasyik: listing passes {'gallery_dl_invocations': 2, 'yt_dlp_invocations': 0, 'direct_api_requests': 8}
lasikasyik: 182 items available, 0 selected for this run
observations_recorded: 182   observations_skipped_no_counts: 0   observations_failed: 0
```

**0 selected, 182 observed.** Under the pre-feature behaviour this run would have
recorded nothing at all — that single line is the feature working.

Derivation over the resulting series:

```
velocity-derive: items=957 derived=42 updated=0 withheld_too_short=0 insufficient_observations=915
```

Sample intervals, with genuinely irregular spacing:

| days | Δlikes | likes/day | rate × days |
|---|---|---|---|
| 18.37 | 58 | 3.157 | 58.00 |
| 1.64 | 5 | 3.050 | 5.00 |
| 18.37 | 18 | 0.980 | 18.00 |

The top two rows are the whole point: **58 likes and 5 likes are nearly the same
velocity** (3.16 vs 3.05/day) because one accrued over 18 days and the other over
1.6. Ranking on raw deltas would have called the first eleven times better.
`rate × days` reconstructs `Δlikes` exactly on every row, proving measured elapsed
time is used rather than observation position.

An unplanned benefit: 140 of the 182 observed items had **never been harvested** —
they sit outside the 31-day collection window but well inside listing reach. They
now accumulate metric history despite never being downloaded or analyzed.

## What to check next cycle (on/after 2026-09-02)

```bash
docker exec postgres psql -U noktah -d noktah_dashboard -c "
  SELECT reason, count(*) FROM velocity_status GROUP BY 1 ORDER BY 2 DESC;"
```

Expected movement:

- a substantial share of the 567 reachable rows leaving `legacy_only` for
  `has_velocity` (or `observed_once` where the account was skipped);
- roughly 252 rows appearing as `no_longer_observable`;
- `UNRESOLVED` still **0** — any other value is a defect;
- `observations_recorded` non-zero in the harvest summary while
  `items_collected` stays near zero, and `request_stats` unchanged from this
  month (SC-003).

Also re-check analysis integrity after the first harvest that exercises the
refresh path in anger:

```bash
docker exec postgres psql -U noktah -d noktah_dashboard -c "
  SELECT count(*) FILTER (WHERE summary IS NOT NULL AND btrim(summary) <> '') AS has_summary,
         count(*) FILTER (WHERE content_flow IS NOT NULL AND btrim(content_flow) <> '') AS has_flow,
         count(*) AS total FROM harvested_signals;"
```

Any decrease from 806 is an FR-010a regression and a hard stop.
